# Ручной smoke-чек-лист GCodeGenerator

**Назначение:**
- первичный «as-is» прогон — базовая линия поведения до рефакторинга (фаза 0, п. 0.8);
- регрессионная проверка **после каждого PR фаз 1–8** (обязательно, см. Plan.md §8);
- после любого изменения, видимого пользователю (диалоги, список операций, опции карманов, требования к ОС).

## Подготовка

1. Сборка: `msbuild GCodeGenerator.sln /p:Configuration=Release` (или IDE).
2. Запуск: `GCodeGenerator\bin\Release\GCodeGenerator.exe`.
3. Эталонный G-код (для пункта 5): `GCodeGenerator.Core.Tests/Reference/reference_project.nc`
   (эталонный набор, п. 0.7 плана; проект — `reference_project.ygc`).
   Автоматическая проверка эталона — тест `ReferenceProjectTests`
   (G-код из `.ygc` через реальный пайплайн сравнивается с `.nc` построчно).

## Чек-лист

Для каждого пункта: ☐ ок / ☐ проблема (описать в журнале).

1. **Операции.** Создать по одной операции каждого вида (9 сверл, 6 профилей, 4 кармана) → параметры → OK.
   Ожидается: для каждого вида открывается свой диалог; операция появляется в списке с описанием.
2. **Диалоги.** Переименовать операцию → двойной клик → открывается **верный** диалог.
   Ожидается: имя сохраняется; двойной клик открывает диалог именно этого вида операции.
3. **Список.** Изменить порядок операций (вверх/вниз), удалить, отключить/включить (`IsEnabled`) → 2D-превью обновляется.
   Ожидается: порядок совпадает в списке и в G-коде; отключённая операция не попадает в G-код; превью перерисовывается.
4. **2D-превью.** Зум колесом, панорама, hover, выбор кликом, «показать всё».
5. **G-код.** Сгенерировать → сравнить с эталоном (diff) → сохранить `.nc`.
   Для эталонного проекта — diff с `Reference/reference_project.nc`.
   (Автоматизировано: тест `Reference_Project_GCode_Matches_Reference_File`.)
6. **3D-превью.** Форма траекторий совпадает со старой (эталонные программы), вращение/зум.
7. **Карманы.** Каждая стратегия (Spiral/Concentric/Radial/ZigZag/Lines) + roughing/finishing → корректный G-код и превью.
   ⚠️ «As-is» (до фазы 5): работает только **Spiral**; остальные стратегии и roughing/finishing — нерабочие
   (решение D1, п. 5 плана) — текущее поведение зафиксировать в журнале.
8. **Проект.** Сохранить → выйти → открыть → все операции/параметры/порядок сохранены.
   ⚠️ «As-is» (до фазы 8, D4): настройки шпинделя/СОЖ **не** входят в `.ygc` (глобальные, `Properties.Settings`) — зафиксировать как есть.
   (Автоматизировано: round-trip тесты `ProjectFileServiceTests`.)
9. **Старый `.ygc`.** Открыть файл проекта, сохранённый до рефакторинга → всё работает.
   (Автоматизировано: round-trip тесты + эталонный `Reference/reference_project.ygc`.)
10. **Настройки.** Все переключатели (линейные номера, padded G, дуги, шпиндель, СОЖ, WCS, G92) → G-код меняется ожидаемо.
    (Автоматизировано: golden-фикстуры `NoLineNumbers`, `PaddedGCodes`, `ArcsOff`, `SpindleCoolantOff`, `WcsG55`, `G92StartEnd`.)
11. **Тема.** Светлая/тёмная → переключение без артефактов, 2D-превью перерисовывается.
12. **Импорт DXF** (профиль и карман): валидный файл, файл без контуров, битый файл → корректные сообщения.
    Образцы: `GCodeGenerator.Core.Tests\Assets\profile_sample.dxf`, `pocket_sample.dxf`.

## Известные проблемы «as-is» (до рефакторинга)

- Стратегии карманов, кроме Spiral, и roughing/finishing — нерабочие (D1 → фаза 5).
- Настройки шпинделя/СОЖ не сохраняются в `.ygc` (D4 → фаза 8).
- DXF-парсер: CIRCLE-контур кармана дублируется; LWPOLYLINE теряет вершины после первой
  (зафиксировано в 0.3, исправление — фаза 4).
- Формат `.ygc`: в `AssemblyQualifiedName` зашита версия сборки — файл, сохранённый сборкой
  с версией (YBUILD), может не открыться в сборке 0.0.0.0 (типы не разрешаются, операции
  пропускаются молча; зафиксировано в 0.7, исправление — п. 1.2).
- «Фантомная фрезеровка»: DXF-контур меньше фрезы фрезеруется (bowtie-артефакт оффсета
  проходит все критерии отсечки; зафиксировано в 0.5, исправление — фаза 4/5).
