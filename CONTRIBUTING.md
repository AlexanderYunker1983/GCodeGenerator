# Как участвовать в проекте

Спасибо за интерес к GCodeGenerator. Ниже — то, что нужно знать до первого
изменения: правила у репозитория строже обычного, и часть из них проверяется
автотестами, а не глазами.

## Сообщить об ошибке или предложить возможность

Заведите [issue](https://github.com/AlexanderYunker1983/GCodeGenerator/issues/new/choose).
Формы две — «Ошибка» и «Предложение»; поля в них — то, без чего разбор
всё равно начнётся с уточняющих вопросов.

К сообщению об ошибке приложите журнал работы:
`%LOCALAPPDATA%\GCodeGenerator\logs\gcodegenerator.log`. Его путь и кнопка
«показать файл» есть в окне «О программе» (F1) — искать в недрах профиля
не нужно. В журнале остаётся текст исключения, который иначе теряется вместе
с закрытым окном сообщения.

Об уязвимости — не через issue: см. [SECURITY.md](SECURITY.md).

## Собрать и проверить

Нужен **.NET 10 SDK**; точная версия закреплена в `global.json`.

```bash
dotnet restore GCodeGenerator.sln --locked-mode
dotnet build GCodeGenerator.sln -c Release
dotnet test GCodeGenerator.sln -c Release
```

Восстановление идёт по замку (`packages.lock.json`). Меняете версию пакета —
обновляйте замок восстановлением всего решения сразу:
`dotnet restore GCodeGenerator.sln --force-evaluate`.

Дерево пакетов сверяется с базой уязвимостей — на каждом прогоне CI и по
требованию:

```powershell
build\Test-VulnerablePackages.ps1
```

Проверка смотрит и прямые, и транзитивные зависимости: уязвимость приходит
через зависимость зависимости чаще, чем через пакет, названный проектом.
Ответ полон настолько, насколько полны источники пакетов: частное зеркало,
не отдающее записей об уязвимостях, промолчит.

## Закреплённые зависимости

**ControlzEx остаётся на 4.4.0.** Актуальная ветка — 7.x, но `MahApps.Metro`
2.4.11 объявляет зависимость `[4.4.0, 6.0.0)`, то есть выше 5.x не пускает
вовсе, а 6.x и 7.x требуют другого MahApps. Уязвимостей в 4.4.0 нет —
проверка дерева пакетов идёт на каждой сборке, — поэтому это не дефект,
а известная граница.

Снять её можно только сменой оформления окон, и решаться это будет вместе
с переходом к версии 2.x: MahApps работает лишь под Windows, а 2.x обещана
кроссплатформенной. Пока предложения Dependabot поднять ControlzEx до
большой версии закрывать нечем — они и не приходят: в его настройке такие
обновления пропускаются, и ссылка на этот раздел лежит рядом с правилом.

## Правила, которые ломают сборку

- **Предупреждений быть не должно.** Включены `TreatWarningsAsErrors` и
  `EnforceCodeStyleInBuild`, поэтому даже неиспользуемая директива `using`
  (IDE0005) останавливает сборку.
- **`#nullable enable` в каждом файле.** Проверяется тестом, а не соглашением.
- **View-модели не знают о WPF.** В них нет типов `System.Windows.*`, нет
  работы с файлами и нет `new XxxService(...)`: зависимости приходят через
  конструктор. Каждое из этих правил закреплено тестом
  (`ArchitectureRulesTests`).
- **Собственные тексты продукта английские.** Строковых литералов на кириллице
  во view-моделях нет: всё, что видит пользователь, лежит в
  `Resources/LocalizableResources.resx` и `.ru.resx`, и наборы ключей в них
  обязаны совпадать.
- **Ядро не зависит от интерфейса.** `GCodeGenerator.Core` — чистый BCL:
  ни WPF, ни MahApps, ни Autofac.

## Эталонные файлы

Программа сверяется с эталонами построчно: `GCodeGenerator.Core.Tests/Golden`
(по операции и набору настроек) и `GCodeGenerator.Core.Tests/Reference`
(эталонный проект целиком). Если изменение вывода намеренное, обновите их
и **посмотрите на разницу**: она должна состоять ровно из того, что вы меняли.

```powershell
$env:GCG_WRITE_GOLDEN = "1"
dotnet test GCodeGenerator.Core.Tests -c Release --filter Write_Golden_Files

$env:GCG_WRITE_REFERENCE = "1"
dotnet test GCodeGenerator.Core.Tests -c Release --filter Write_Reference_Set
```

## Тесты

Изменение поведения приходит вместе с проверкой. Полезно проверить и саму
проверку: верните дефект и убедитесь, что новый тест падает. Тест, который
проходит на сломанном коде, не проверяет ничего.

Есть и ручной прогон — [docs/SMOKE_CHECKLIST.md](docs/SMOKE_CHECKLIST.md):
в нём то, чего автотесты не видят, — как выглядит и ведёт себя окно.

## Pull request

1. Ветка от `master`.
2. Сборка Release без предупреждений, все тесты зелёные.
3. Заметное для пользователя изменение — строкой в разделе «Не выпущено»
   файла [CHANGELOG.md](CHANGELOG.md).
4. Сообщение коммита по-русски, одним абзацем: что было не так, почему это
   важно и что изменилось. Такой текст читается через год; «fix bug» — нет.

## Выпуск

Выпуск делает владелец репозитория: push тега `X.Y.Z` (или `X.Y.Z-rc5`)
запускает рабочий процесс [Release](.github/workflows/release.yml) — сборка,
тесты, установщик и GitHub Release. Перед тегом раздел «Не выпущено» в
CHANGELOG переименовывается в номер версии: описание выпуска берётся именно
из него.

До первого тега в настройках репозитория должна быть включена опция
**Releases → Immutable releases**. Workflow сначала заполняет draft всеми
артефактами, публикует его и затем проверяет release attestation и каждый
asset; отсутствие immutability считается ошибкой выпуска. Повторная загрузка
файла с тем же именем запрещена, поэтому исправленный кандидат получает новый
tag, а не заменяет уже опубликованный.

Пока публично доверенного сертификата нет, официальный workflow явно вызывает
`build\Make-Installer.ps1 -SigningMode Unsigned` и не получает секретов
подписи. Это осознанное свойство выпуска, а не молчаливый fallback. После
появления сертификата отдельное изменение должно подключить защищённый key
store, закрепить ожидаемый thumbprint и переключить workflow на
`-SigningMode Required`; смешивать эту миграцию с выпуском нельзя.

После завершения job скачайте `SHA256SUMS.txt` и хотя бы один исполняемый
asset, затем независимо выполните `gh release verify <tag>` и
`gh release verify-asset <tag> <путь-к-файлу>`. Ручная проверка установщика и
обновления описана в [docs/SMOKE_CHECKLIST.md](docs/SMOKE_CHECKLIST.md).
